## 오전: 에러와 예외 - 1.1

| 구분 | 설명 | 처리 가능 여부 |
|------|------|--------------|
| **Error** | 시스템 수준 복구 불가능한 심각한 문제 (OutOfMemoryError, StackOverflowError 등) | ❌ 개발자가 수습 불가 |
| **Exception** | 애플리케이션 수준에서 발생하는 비교적 가벼운 오류 | ✅ 코드로 처리 가능 |

```java
// StackOverflowError 발생 예시 (재귀 호출)
static void makeError(){
    makeError(); // 무한 재귀 → 스택 메모리 초과
}

try{
    makeError();
}catch(Throwable t){ // Error도 잡으려면 Throwable로
    System.out.println("에러 발생: " + t.getClass().getSimpleName());
}
```

> 일반적으로 `Error`는 catch하지 않는다. JVM이 복구 불가능한 상태이기 때문.

## 오전: 예외 계층 구조 - 1.2

```
Throwable
├── Error                 → StackOverflowError, OutOfMemoryError
└── Exception
    ├── Checked Exception  → IOException, SQLException, FileNotFoundException
    │   (RuntimeException 제외한 나머지)
    └── RuntimeException   → Unchecked Exception
        → NullPointerException, ArithmeticException, IndexOutOfBoundsException
```

| 구분 | Checked Exception | Unchecked Exception |
|------|-----------------|-------------------|
| 처리 여부 | 반드시 처리 (컴파일 강제) | 처리 강제 안 함 |
| 확인 시점 | 컴파일 시점 | 실행 시점 (Runtime) |
| 대표 클래스 | IOException, SQLException | NullPointerException, ArithmeticException |
| 주요 원인 | 외부 자원 연동 (DB, 파일 등) | 개발자 코드 로직 오류 |

## 오전: try-catch-finally - 1.3

```java
void divide(int num1, String[] arr){
    try{
        int num2 = arr[0].trim().length(); // NullPointerException 또는 ArrayIndexOutOfBoundsException
        int result = num1 / num2;          // ArithmeticException
        System.out.println(num1 + " / " + num2 + " = " + result);
        return;
    }catch(ArithmeticException e){
        System.out.println("0으로 나눌 수 없습니다.");
    }catch(NullPointerException e) {
        System.out.println("arr[0]이 null입니다.");
        return;
    }catch(ArrayIndexOutOfBoundsException e){
        System.out.println("arr 사이즈가 0입니다.");
    }finally{
        System.out.println("finally는 try-catch 블럭이 실행된 뒤 항상 실행을 보장.");
    }

    System.out.println("finally 블럭과 try-catch 다음줄에 실행되는 코드는 무슨차이???");
}
```

**`finally` vs try-catch 다음 줄 차이**

| | finally | try-catch 다음 줄 |
|-|---------|-----------------|
| `return` 있을 때 | ✅ 실행됨 | ❌ 실행 안 됨 |
| 예외 없을 때 | ✅ 실행됨 | ✅ 실행됨 |
| 예외 있을 때 | ✅ 실행됨 | ✅ 실행됨 (catch 처리 후) |

> `return`이 있어도 `finally`는 반드시 실행 — 그래서 자원 해제에 `finally`를 사용.

## 오전: 다형성을 이용한 예외 처리

catch 블록에 상위 예외 클래스를 지정하면 하위 예외를 모두 잡을 수 있다. 단, **반드시 하위 클래스를 먼저** 작성해야 한다.

```java
// ✅ 올바른 순서: 하위 예외 먼저
try { ... }
catch(ArrayIndexOutOfBoundsException e){ System.out.println("배열 범위 초과"); }
catch(Exception e){ System.out.println("그 외의 예외"); }

// ❌ 잘못된 순서: 상위 예외가 먼저면 컴파일 에러
try { ... }
catch(Exception e){ System.out.println("모든 예외"); }
catch(NullPointerException e){ ... } // Unreachable catch block 컴파일 에러!
```

## 오전: Multi-catch - 1.3

자바 7부터 `|` 기호로 여러 예외를 하나의 catch 블록에서 처리.

```java
// Multi-catch
catch(ArithmeticException | NullPointerException e){
    System.out.println(e.getMessage());
}
```

**catch 작성 스타일 4가지 비교 (MultiCatchTest)**

```java
// divide()  - 멀티 캐치 + 별도 catch
catch(ArithmeticException | NullPointerException e){ ... }
catch(ArrayIndexOutOfBoundsException e){ ... }

// divide2() - 하위 먼저, 상위 나중
catch(ArrayIndexOutOfBoundsException e){ ... }
catch(Exception e){ ... }

// divide3() - Exception 하나로 다 잡기
catch(Exception e){ ... }

// divide4() - try-catch 없이 if문으로 방어 (예외 자체를 만들지 않음)
if(arr != null && arr.length > 0 && arr[0] != null && arr[0].trim().length() > 0){
    ...
}
```

> 실무에서는 예외를 잡는 것보다 `divide4()`처럼 **예외가 발생하지 않도록 방어적으로 코드를 작성**하는 게 더 좋다.

## 오전: try-with-resources

자바 7에서 도입. `AutoCloseable`을 구현한 자원을 `try(...)` 안에 선언하면 블록 종료 시 자동으로 `close()` 호출.

```java
// 기존 방식 — finally에서 수동 해제
Connection conn = null;
Statement stmt = null;
try{
    conn = DriverManager.getConnection(...);
    stmt = conn.createStatement();
    stmt.executeUpdate(sql);
}catch(Exception e){
    ...
}finally{
    try{ if(stmt != null) stmt.close(); } catch(Exception e){}
    try{ if(conn != null) conn.close(); } catch(Exception e){}
}

// try-with-resources — 자동 해제
try(Connection conn = DriverManager.getConnection(...);
    Statement stmt = conn.createStatement()){
    stmt.executeUpdate(sql);
}catch(Exception e){
    ...
}
// 블록 종료 시 stmt.close() → conn.close() 자동 호출
```

> `Connection`, `Statement`, `ResultSet` 모두 `AutoCloseable`을 구현하고 있어서 try-with-resources로 관리 가능.

## 오전: Java에서 트랜잭션 제어 (JdbcMemberTest)

`Connection`의 메서드로 Java 코드에서 직접 트랜잭션 제어 가능.

```java
conn = DriverManager.getConnection(...);

// 자동 커밋 끄기 (= START TRANSACTION)
conn.setAutoCommit(false);

try{
    stmt.executeUpdate("DELETE FROM post WHERE member_id=" + id);
    stmt.executeUpdate("DELETE FROM member WHERE id=" + id);
    conn.commit();   // 성공 시 영구 반영
}catch(Exception e){
    conn.rollback(); // 실패 시 원래 상태로 복구
}
```

| SQL (DBeaver) | Java (JDBC) |
|---------------|-------------|
| `START TRANSACTION` | `conn.setAutoCommit(false)` |
| `COMMIT` | `conn.commit()` |
| `ROLLBACK` | `conn.rollback()` |

## 오후: throw와 throws - 1.4

### throw — 예외를 직접 발생시키기

개발자가 로직 내부에서 명시적으로 예외 객체를 생성하여 던질 때 사용.

```java
public static void insertMember(String email, String password, String name, String phone, int recommenderId)
        throws IllegalArgumentException {

    if(phone.length() > 11){
        throw new IllegalArgumentException("phone은 11자 이내여야 합니다.");
    }
    // ... DB 처리
}
```

**주요 사용 시점:**
- 전달받은 아규먼트가 비즈니스 규칙에 위배될 때 (예: 음수 나이, 하이픈 포함 전화번호)
- 비즈니스 로직 흐름 진행이 불가능할 때 (예: 잔액 초과 출금)
- 시스템 예외(SQLException)를 비즈니스 의미가 담긴 사용자 정의 예외로 재포장할 때

### throws — 예외 처리를 호출자에게 전가하기

메서드 선언부에 작성. 해당 메서드에서 발생할 수 있는 예외를 명시하고 처리 책임을 호출자에게 넘김.

```java
// insertMember가 throws IllegalArgumentException을 선언했으므로
// 호출자(main)에서 try-catch 처리
try{
    insertMember("haru@gmail.com", "1234", "하루", "010-2222-3333", 2);
}catch(IllegalArgumentException e){
    System.out.println(e.getMessage());
    // 하이픈 제거 후 재시도
    insertMember("haru@gmail.com", "1234", "하루", "010-2222-3333".replace("-", ""), 2);
}
```

**무분별한 `throws Exception` 사용의 문제점:**
- 어떤 예외가 발생하는지 파악 불가
- 호출 측에서 유의미한 예외 처리 불가능
- 반드시 발생 가능한 구체적인 예외 타입을 명시해야 함

**예외 재발생 (Re-throwing):**  
catch 블록에서 처리 후 다시 `throw`로 던져 호출자에도 예외 사실을 전달.

## 오후: 사용자 정의 예외 - 1.5

비즈니스 요구사항에 맞는 명확한 이름의 예외 클래스를 직접 정의.

```java
// LoginFailException.java
public class LoginFailException extends Exception {
    public LoginFailException(String message) {
        super(message);
    }
}
```

```java
// login() 메서드에서 사용
public static void login(String email, String password) throws LoginFailException {
    if(email == null || email.isBlank() || password == null || password.isBlank()){
        throw new LoginFailException("email과 password를 확인하세요.");
    }
    // ... DB 처리
}

// 호출 측
try {
    login("haru@gmail.com", "    ");
} catch (LoginFailException e) {
    System.out.println(e.getMessage());
}
```

**현대 자바 예외 처리 트렌드:**

| 구분 | 설명 |
|------|------|
| Checked Exception 상속 | 호출자에게 처리 강제 → 코드 복잡도 증가 |
| **RuntimeException 상속** | **처리 유연, Spring 등 현대 프레임워크의 표준** |

> 무분별한 사용자 정의 예외 선언 지양. `IllegalArgumentException`, `IllegalStateException` 등 **표준 예외를 우선 재사용** 권장.

## 오후: List — ArrayList vs LinkedList - 2.2

**공통 특징:** 순서 유지, 중복 허용

| 항목 | ArrayList | LinkedList |
|------|-----------|------------|
| 내부 구조 | 가변 배열 | 이중 연결 리스트 |
| 인덱스 조회 | 빠름 | 처음부터 순회 필요 (느림) |
| 중간 삽입/삭제 | 기존 요소 이동 필요 (느림) | 링크 주소만 변경 (빠름) |
| 메모리 사용량 | 적음 | 많음 (앞뒤 노드 참조 저장) |

```java
List<String> arrayList = new ArrayList<>();
arrayList.add("Java");
arrayList.add("Spring");
arrayList.add(1, "React"); // [Java, React, Spring] — 기존 요소 뒤로 밀림

List<String> linkedList = new LinkedList<>();
linkedList.add("Docker");
linkedList.add(0, "AWS"); // [AWS, Docker] — 링크 관계만 재구성
```

## 배운점

1. ✅ Error는 JVM 수준 복구 불가 — 개발자가 처리할 수 없고 `StackOverflowError`, `OutOfMemoryError` 등이 해당.
2. ✅ Checked Exception은 컴파일러가 처리를 강제 (외부 자원 연동), Unchecked는 코드 로직 오류가 원인.
3. ✅ 다중 catch는 반드시 하위 예외 클래스부터 — 상위가 먼저면 컴파일 에러.
4. ✅ `finally`는 `return`이 있어도 반드시 실행 — try-catch 다음 줄과의 핵심 차이.
5. ✅ Multi-catch(`|`)로 같은 처리를 묶어서 코드 중복을 줄일 수 있다.
6. ✅ `divide4()`처럼 예외 자체가 발생하지 않도록 if문으로 방어하는 게 더 좋은 코드다.
7. ✅ try-with-resources로 `finally` 없이도 자원 자동 해제 — 코드가 훨씬 깔끔해진다.
8. ✅ Java에서도 `conn.setAutoCommit(false)` / `commit()` / `rollback()`으로 트랜잭션 제어 가능.
9. ✅ `throw`는 예외를 발생, `throws`는 처리 책임을 호출자에게 전가 — 둘은 역할이 다르다.
10. ✅ 사용자 정의 예외는 RuntimeException 상속이 현대 트렌드 — 표준 예외 우선 재사용 권장.
11. ✅ 컬렉션 프레임워크에서 Map은 Collection과 별개 계층 — Key-Value 구조라 다르게 설계됨.
12. ✅ ArrayList는 조회가 빠르고 LinkedList는 중간 삽입/삭제가 빠름 — 용도에 따라 선택.
13. ✅ LinkedHashSet은 중복 제거 + 삽입 순서 유지 — HashSet(순서 없음), TreeSet(정렬)과 차이가 있다.

## 오늘 핵심 정리

```
예외 계층
  Throwable → Error (복구 불가) / Exception (처리 가능)
  Checked   → 컴파일 강제, 외부 자원 관련 (IOException, SQLException)
  Unchecked → 런타임, 코드 로직 오류 (NullPointerException, ArithmeticException)

try-catch-finally
  catch 순서: 하위 예외 먼저 → 상위 예외 나중 (반대면 컴파일 에러)
  finally: return이 있어도 항상 실행 → 자원 해제에 사용
  Multi-catch: catch(A | B e) 로 여러 예외를 하나의 블록에서 처리

try-with-resources
  try(자원 선언){ ... } → 블록 종료 시 자동 close()
  AutoCloseable 구현체에만 적용 가능 (Connection, Statement, ResultSet 등)

Java 트랜잭션 제어
  conn.setAutoCommit(false) → 수동 트랜잭션 시작
  conn.commit()             → 영구 반영
  conn.rollback()           → 원래 상태로 복구

throw / throws
  throw new XxxException("메시지") → 예외를 직접 발생
  throws XxxException              → 처리 책임을 호출자에게 전가
  사용자 정의 예외: RuntimeException 상속 권장, 표준 예외 우선 재사용

컬렉션 프레임워크
  List  → 순서 유지, 중복 허용 (ArrayList: 조회 빠름 / LinkedList: 삽입·삭제 빠름)
  Set   → 중복 불허 (HashSet: 순서 없음 / LinkedHashSet: 삽입 순서 / TreeSet: 정렬)
  Map   → Key-Value, Collection과 별개 계층 (HashMap, LinkedHashMap, TreeMap)
```
